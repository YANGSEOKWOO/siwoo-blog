CPU는 자바 코드를 직접 이해하지 못합니다. CPU가 아는 건 기계어뿐이고, 기계어는 **CPU 종류와 OS마다 다릅니다.** 그래서 자바는 중간 언어인 **바이트코드**로 한 번만 컴파일하고, OS마다 설치된 JVM이 그 바이트코드를 실행합니다.

<JvmPipeline />

> 비유: 바이트코드는 **영어로 쓴 대본**이고, JVM은 나라마다 있는 **통역사**입니다.
> 또는 게임 **에뮬레이터**를 떠올려도 됩니다. JVM이 에뮬레이터이고 내 자바 프로그램이 게임입니다. "가상 머신"이라는 이름이 여기서 나왔습니다.

**`java Hello`를 실행하면 일어나는 일**

1. **클래스 로더**: `Hello.class` 파일을 읽어 메모리에 올립니다 (필요할 때마다).
2. **바이트코드 검증**: 메모리를 함부로 건드리는 코드 같은 이상한 코드가 아닌지 검사합니다.
3. **실행 엔진**: 처음에는 **인터프리터**가 한 줄씩 통역하며 실행합니다. 자주 도는 코드는 **JIT 컴파일러**가 통째로 기계어로 번역하고 최적화해 둡니다.
4. **가비지 컬렉터**: 더 이상 안 쓰는 객체를 자동으로 치웁니다.

JIT의 최적화는 빠르지만, 여러 스레드가 함께 쓰는 값을 예상과 다르게 다룰 수 있습니다. [volatile](#term-volatile)이 필요한 이유 중 하나입니다.

**JVM이 동시성에서 하는 일**

| 개념 | JVM이 하는 일 |
|---|---|
| `new Thread().start()` | OS에 요청해서 OS 스레드를 하나 만들고 연결 ([플랫폼 스레드](#term-platform-thread)) |
| `synchronized` | 컴파일러가 넣은 `monitorenter`/`monitorexit`대로 실제로 잠그고 풂 |
| 모든 객체가 락을 가짐 | 객체를 만들 때마다 헤더에 잠금 상태를 기록할 자리를 둠 ([모니터](#term-monitor)) |
| `volatile` | 최적화하더라도 이 변수는 매번 최신 값을 읽도록 지킴 |
| 가상 스레드 | OS가 아니라 **JVM이 직접** 만들고 관리하는 스레드 |

**프로그램과 프로세스**

JVM이라는 말은 두 가지 뜻으로 쓰입니다. 디스크에 설치된 **프로그램**(`java.exe`, `jvm.dll`)을 가리키기도 하고, 그것을 **실행한 프로세스**를 가리키기도 합니다. 동시성 이야기에서는 보통 **실행 중인 JVM 하나 = java 프로세스 하나**를 뜻합니다.

JDK를 설치하면 컴파일된 바이트코드를 직접 볼 수 있습니다.

```bash
javac Counter.java   # 바이트코드(.class) 만들기
javap -c Counter     # 바이트코드 들여다보기
```
