- **라이브러리 함수**: `Math.max()`, `list.add()`처럼 누군가 **작성해 둔 평범한 메서드**입니다. 원하면 똑같은 걸 직접 만들 수도 있습니다. 컴파일러 입장에서는 그냥 "메서드 호출"일 뿐입니다.
- **언어 문법(키워드)**: `if`, `for`, `try`, `synchronized`처럼 **언어가 처음부터 정해 둔 규칙**입니다. 직접 만들거나 다른 뜻으로 바꿀 수 없고(`int if = 3;`은 컴파일 오류), 컴파일러가 **그 의미를 알고** 필요한 코드를 넣어 줍니다.

자바에는 잠금 방법이 두 가지 있어서 바로 비교할 수 있습니다.

<Compare left="라이브러리 · ReentrantLock" right="문법 · synchronized" leftTone="warn" rightTone="ok">

```java
lock.lock();       // 잠그기
try {
    count++;
} finally {
    lock.unlock(); // 반납 (직접)
}
```

```java
synchronized (lock) { // 잠그기
    count++;
}                     // 자동 반납
```

</Compare>

- **라이브러리 방식**은 `unlock()`을 깜빡하거나 `finally` 없이 써도 **컴파일러가 아무 경고도 하지 않습니다.** 그러면 다른 스레드들이 영원히 기다리게 됩니다.
- **문법 방식**은 컴파일러가 예외가 나는 경우까지 포함해서 반납 코드를 넣어 주기 때문에 **반납을 깜빡하는 일이 구조적으로 생길 수 없습니다.**

> 비유: 라이브러리는 철물점에서 산 **자물쇠**입니다. 잠그는 것도 푸는 것도 내 몫입니다.
> 언어 문법은 건물 설계에 들어간 **자동문**입니다. 들어가면 잠기고 나오면 열립니다.

**왜 이게 자바의 특징일까요?**

옛날 C 언어는 언어 자체에 스레드나 잠금이라는 개념이 없어서, OS가 주는 라이브러리 함수(`pthread_mutex_lock`)를 불러야 했습니다. 자바는 처음부터 `synchronized`를 **문법으로** 넣었습니다. 언어가 멀티스레드를 직접 책임지겠다고 설계한 것입니다.

`ReentrantLock`이 위험하다는 뜻은 아닙니다. 대기 시간 제한 같은 기능이 더 많아서 실무에서 많이 씁니다. 차이는 **반납을 내가 책임지느냐, 언어가 책임지느냐**입니다.
